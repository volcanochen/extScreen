## 扩展屏竖屏铺满 —— 找到根因并修好

**用户反馈**：屏幕竖着放，却显示横着的桌面。

### 根因（不是渲染 bug，是请求分辨率是横的）

`dumpsys display` 全程 `rotation 0`（方向补丁是生效的），但 Moonlight 的
`Configuring with format` 里是 `width=2192, height=1088` —— **横屏**。
Sunshine 捕获 (1080x2220) 和 PC 端虚拟屏都是对的，是客户端请求错了：

`PreferenceConfiguration.readPreferences` 里我上次插入的宽高交换分支写反了：
`if-gt v3, v4, :cond_es_portrait`（宽>高才跳过交换）→ 无论屏幕怎么放都得到横屏。
正确写法是 `if-ge v4, v3, :cond_es_portrait`（高>=宽才跳过）。

横屏流塞进竖屏窗口 → aspect-fit → 高度只剩 ~24%，看起来就是"屏幕中间一小块"。
之前误判为"渲染成 1/4 方块"，其实是横向 letterbox，wallpaper 边缘偏暗导致
按亮度阈值测 bbox 时只框到了亮的中间部分。

### 三处改动（都在 `tools/ml_src`）

1. 宽高交换方向修正 → 请求 1080x2180（2180 = 2220 减导航栏 40）
2. 去掉 16 对齐（原来会把 1080x2220 撑成 1088x2224，和虚拟屏不等比例）
3. `stretchVideo` 强制 true → 走 `holder.setFixedSize` 分支铺满，
   否则流 2220 vs 窗口 2180 的 1.8% 差值还会留黑边

结果：填充 98.3% × 100%，只剩左右各 9px 细黑边。

### 手机端 UI 自动化的坑（重要）

这台 Note8 上 `adb shell input tap` / `input touchscreen tap` **会被当成
长按**（input dispatcher 会卡"Waiting for application to become ready"，
DOWN 带的是陈旧时间戳，超过 500ms 长按阈值）。在 Moonlight 的 AppView 里
表现为弹「恢复串流 / 退出串流 / 查看详情 / 创建快捷方式」菜单，点头像根本
进不去串流。点菜单项反倒能用（列表项没有 long-click 监听，UP 仍触发 click）。

**可靠做法：走 `ShortcutTrampoline`，完全不碰界面**
```
adb shell am start -n com.limelight/.ShortcutTrampoline \
  -e UUID 31D8D607-8EA8-1805-3498-573BF705B4E4 \
  -e AppId 881448767 -e AppName Desktop
```
三个 extra 都是**字符串**。UUID 从 `adb logcat -d | grep "is UUID"` 抓。

### 显示器布局（别踩的坑）

物理坐标（DEVMODE / `EnumDisplaySettings`）：
```
DISPLAY1    (0,    0)    3440x1440  主屏
DISPLAY2    (3440, -740) 3840x2160
DISPLAY117  (7280, 0)    1080x2220  虚拟屏   ← 7280 == 7280，紧贴 DISPLAY2
```
看着像中间空 1440px，其实**没有死区**，鼠标能跨过去。
坑在于 `EnumDisplayMonitors` 在非 per-monitor DPI aware 下返回的是**逻辑坐标**
（DISPLAY2 会报成 2400x1350，因为它是 4K@160%），按那个判断就会误以为显示器不相邻。
判断相邻一律用 DEVMODE 的物理坐标。

## 2026-11-02 02:00 托盘状态真实性修复（用户报告"显示已启动但没串流/又显示已关闭"）

用户原话：「dock 显示已启动时，实时还没起来，然后过一会 sunshine 启动后，显示已关闭」
并纠正方向：「不是去测量时差，是真正去检查是否已经启动！！」

### 根因一：SCM 服务状态 ≠ 应用就绪

`service_state()==SERVICE_RUNNING(4)` 只说明 SunshineService 进程活着。Sunshine 起来后
还要枚举显示器 → 编译 shader → 建 NVENC → 起 HTTP → 注册 mDNS，**实测空窗 20~30 秒**。
这段空窗里旧逻辑一直显示"已启动"，是用户报告问题的直接根源。

**判据设计（不是时间差，是真实探针）**：
- 就绪标志 `Registered Sunshine mDNS service`（初始化最后一步）
- 备选 `Configuration UI available at`
- 退出标志 `Unregistered Sunshine mDNS service`
- 客户端 `CLIENT CONNECTED` / `CLIENT DISCONNECTED`

### 根因二：开关判定反向，导致"再点一次反而关掉"

`toggle_extscreen` 用 `vdd or svc==RUNNING` 判"已开"，用户在空窗期再点一次
→ 走 `disable_extscreen()` → 把扩展屏关了。修复：`extscreen_on()` 只认 `STATE['ready']`。

### 三个日志陷阱（都会造成误报）

1. `sunshine.log` 会滚动成 `.1/.2/.3/.4/.5`，旧文件里的标志属于上一次会话
   → **只读最新的 `sunshine.log`**
2. Sunshine 被服务停止**强杀**时不打印 CLIENT DISCONNECTED，只打印 Unregistered
   → client 判定必须锚定「当前会话」：先找最后一个 READY 位置，只看它之后的
   CONNECTED/DISCONNECTED；若之后出现 STOPPED，直接算没连
3. 重启后新会话未连接时，上一轮 CONNECTED 仍留在日志里 → 同样会误报

### 顺带修掉的两个真 bug

- **`cannot unpack non-iterable bool object`**：`restart_vdd()` 只返回 bool，
  而 `do_async` 按 `(ok, msg)` 解包 → 托盘崩溃。改成二元组 + do_async 加单值兜底 +
  `tools/test_action_contract.py` 锁死契约
- **关闭扩展屏卡死 150 秒**：`Disable-PnpDevice` 会等设备排空，而 Sunshine 的
  DXGI 抓屏句柄还开着 → 永久阻塞，托盘一直显示"处理中…"。三重修复：
  1. `disable_extscreen` 顺序改为**先停 Sunshine 再关虚拟屏**（与 enable 相反）
  2. `Common.ps1` 的 `Set-VddEnabled` disable 改走 `pnputil /disable-device`（实测 2.2 秒），
     `Disable-PnpDevice` 降为兜底（PS 5.1 的 `Disable-PnpDevice` **没有** `-Timeout` 参数）
  3. powershell 调用超时 150 → 60 秒

### 其他改动

- `src/extscreen_core.py`：新增 `start_service_scm()` / `stop_service_scm()`（advapi32 原生 API，
  不再依赖 `sc.exe` 的本地化输出；`sc.exe` 降级为 ACCESS_DENIED 时的兜底）
- `src/extscreen_display.py`：新增 `sunshine_vdd_device_id()` —— 按 EDID 特征
